# Лабораторная работа №2: Гибридное распараллеливание (MPI + OpenMP)
## Решение 3D уравнения Пуассона методом Якоби

Данный репозиторий содержит реализацию и исследование производительности гибридной параллельной программы для решения трёхмерного уравнения Пуассона методом Якоби. Проект разработан в рамках учебного курса по параллельным методам вычислений.

---

## 📋 Описание и ключевые особенности

**Цель работы** — исследовать распараллеливание численного решения трёхмерного уравнения Пуассона методом Якоби с использованием гибридной модели MPI + OpenMP.

**Основные особенности реализации:**

1. **Двумерная декомпозиция области.** Глобальная сетка разбивается на подобласти по осям X и Y с использованием виртуальной декартовой топологии MPI (`MPI_Cart_create`). Ось Z не декомпозируется между MPI-процессами.
2. **Неблокирующие обмены граничными данными.** Для обмена с соседними подобластями используются `MPI_Irecv` и `MPI_Isend`. Полученные значения записываются в ghost-слои, необходимые для вычисления граничных точек.
3. **Перекрытие вычислений и коммуникаций.** После запуска обменов вычисляются внутренние точки локальной подобласти. Такая схема позволяет выполнять полезную работу до завершения коммуникаций.
4. **Двойная архитектура сборки**:
   * `Lab_02`: Основная версия с внутренним профилированием через `MPI_Wtime` для точных замеров времени.
   * `Lab_02_mpe`: Специальная версия с настраиваемым профилированием MPE для генерации трассировочных файлов `.clog2` и визуализации в Jumpshot.
5. **Гибридный параллелизм.** Вложенные циклы вычислений распараллеливаются средствами OpenMP, в том числе с помощью директив `#pragma omp parallel for collapse(3)` для эффективного использования кэш-памяти и векторизации.
6. **Профилирование.** В основной версии измеряется время выполнения этапов алгоритма. Дополнительная версия с инструментированием MPE позволяет записывать трассировку и анализировать временную диаграмму в Jumpshot-4.
7. **Контроль сходимости и точности.** Программа проверяет условие остановки по максимальному изменению решения и вычисляет максимальное отклонение от известного точного решения.
8. **Автоматизация экспериментов и визуализация.** Скрипты Python строят графики времени выполнения, ускорения и эффективности для исследованных конфигураций MPI и OpenMP.
9. **Чистая архитектура**: Код разделён на заголовочный файл (`poisson_solver.hpp`) с документацией Doxygen и файл реализации.
10. **Тройной контроль времени**: Замер времени выполняется одновременно через `MPI_Wtime()`, `omp_get_wtime()` и `std::chrono` для подтверждения корректности метрик.

Названия исполняемых файлов и исходников для основной и MPE-версии должны соответствовать фактической структуре проекта и настройкам `CMakeLists.txt`.

## 💻 Системные требования

* **Документация:** Doxygen (опционально, для генерации docs)

## 🛠️ Сборка проекта

1. Склонируйте репозиторий (если еще не сделали этого):
   ```bash
   git clone <URL этого репозитория>
   cd NSU_Parallel_methods_on_Super_Computers/Lab_02
   ```
2. Создайте директорию для сборки и перейдите в неё:
   ```bash
   mkdir build && cd build
   ```
3. Сконфигурируйте проект в режиме Release (с оптимизацией `-O3`):
   ```bash
   cmake .. -DCMAKE_BUILD_TYPE=Release
   ```
4. Скомпилируйте проект, используя все доступные ядра:
   ```bash
   make -j
   ```
5. Опционально. Сгенерировать Doxygen-документацию:
   ```bash
   make doc
   ```

## 🚀 Запуск и бенчмаркинг
### **Ручной запуск**
Программа принимает три аргумента: размеры сетки по осям X, Y, Z. По умолчанию используется сетка 200×200×200.
   ```bash
   # Запуск основной версии на 4 MPI-процессах
   mpirun --oversubscribe -np 4 ./build/Lab_02 200 200 200
   
   # Запуск MPE-версии для сбора трассировки (сохранит jacobi_profile.clog2)
   mpirun --oversubscribe -np 4 ./build/Lab_02_mpe 200 200 200
   ```

### **Гибридный запуск (Моделирование кластера локально)**

Для поиска оптимальной комбинации «число MPI-процессов × число OpenMP-потоков» используйте переменную окружения `OMP_NUM_THREADS`.
*Пример: 2 MPI-процесса, каждый из которых порождает по 4 OpenMP-потока (всего 8 вычислительных потоков):*

   ```bash
   OMP_NUM_THREADS=4 mpirun -np 2 ./Lab_02 200 200 200
   ```

### **Автоматический гибридный бенчмаркинг**

В корне проекта находится скрипт `benchmark.sh`, который автоматически тестирует различные комбинации MPI-процессов и OpenMP-потоков при фиксированном общем числе потоков, выполняя по 3 запуска для каждой конфигурации и выбирая минимальное время.

   ```bash
   # Сделать скрипт исполняемым (один раз)
   chmod +x benchmark.sh
   
   # Запустить бенчмарк
   ./benchmark.sh
   ```

### Построение графиков

Установите необходимые зависимости Python:

```bash
python3 -m pip install matplotlib pandas seaborn
```

Запустите скрипты из корня проекта:

```bash
python3 visual_scripts/plot_benchmarks2.py
python3 visual_scripts/plot_lab2.py
```

Первый скрипт строит графики с использованием Seaborn, второй — средствами Matplotlib. Результаты сохраняются в каталоге `visualisations/`.

> **Примечание:** перед запуском проверьте, что скрипты действительно находятся в `visual_scripts/`. Если они размещены в другом каталоге, измените команды запуска соответственно.

## 📊 Результаты исследования производительности

Эксперименты проводились на сетке размером **700 × 700 × 700**. В качестве базового значения использовано время выполнения конфигурации `1 MPI × 1 OpenMP`, равное **317,679 с**. Ускорение и эффективность рассчитаны относительно этой конфигурации.

### Чистый MPI

| MPI-процессы | Время, с | Ускорение | Эффективность, % |
|---:|---:|---:|---:|
| 1 | 317,679 | 1,000 | 100,0 |
| 2 | 179,244 | 1,772 | 88,6 |
| 4 | 117,313 | 2,708 | 67,7 |
| 5 | 101,279 | 3,137 | 62,7 |
| 6 | 90,2635 | 3,519 | 58,7 |
| 8 | 112,668 | 2,820 | 35,2 |
| 10 | 113,691 | 2,794 | 27,9 |

В серии чистого MPI наилучшее время показала конфигурация из 6 процессов — **90,2635 с**. При увеличении числа процессов до 8 и 10 время выполнения выросло. Это указывает на то, что увеличение числа процессов не гарантирует ускорения: существенное влияние оказывают накладные расходы обменов и особенности декомпозиции области.

### Гибридный MPI + OpenMP

| MPI × OpenMP | Всего потоков | Время, с | Ускорение | Эффективность, % |
|:---:|---:|---:|---:|---:|
| 1 × 1 | 1 | 317,679 | 1,000 | 100,0 |
| 4 × 1 | 4 | 117,313 | 2,708 | 67,7 |
| 2 × 2 | 4 | 105,580 | 3,009 | 75,2 |
| 1 × 4 | 4 | 182,647 | 1,739 | 43,5 |
| 2 × 4 | 8 | 115,697 | 2,746 | 34,3 |
| 4 × 2 | 8 | 99,9782 | 3,177 | 39,7 |
| 1 × 8 | 8 | 199,593 | 1,592 | 19,9 |
| 8 × 1 | 8 | 112,668 | 2,820 | 35,2 |
| 4 × 4 | 16 | 112,872 | 2,815 | 17,6 |
| 2 × 8 | 16 | 105,558 | 3,010 | 18,8 |
| 8 × 2 | 16 | 86,8708 | 3,657 | 22,9 |
| 1 × 16 | 16 | 191,861 | 1,656 | 10,3 |
| **9 × 2** | **18** | **80,8495** | **3,929** | **21,8** |
| 2 × 9 | 18 | 119,733 | 2,653 | 14,7 |
| 10 × 2 | 20 | 90,986 | 3,492 | 17,5 |
| 10 × 3 | 30 | 117,312 | 2,708 | 9,0 |
| 10 × 4 | 40 | 108,226 | 2,935 | 7,3 |
| 10 × 5 | 50 | 114,849 | 2,766 | 5,5 |
| 10 × 10 | 100 | 135,400 | 2,346 | 2,3 |
| 10 × 20 | 200 | 180,174 | 1,763 | 0,9 |

Для конфигурации `2 × 10` время выполнения в исходных данных отсутствовало, поэтому она не включена в таблицу.

### Основные выводы

1. **Лучшая измеренная конфигурация в представленной гибридной серии — `9 × 2`.** Время выполнения составляет 80,8495 с, а ускорение относительно `1 × 1` — приблизительно **3,93 раза**.
2. **Соотношение MPI-процессов и OpenMP-потоков существенно влияет на производительность.** Например, конфигурации `2 × 2` и `1 × 4` используют по четыре потока, однако показывают разные времена выполнения: 105,580 и 182,647 с соответственно.
3. **Увеличение числа потоков не гарантирует ускорения.** При большом числе потоков возрастают накладные расходы планирования и синхронизации, а также конкуренция за вычислительные ресурсы.
4. **Эффективность зависит от выбранной конфигурации.** В таблице она рассчитана как ускорение, делённое на общее число MPI-процессов и OpenMP-потоков. Поэтому её следует интерпретировать как относительную эффективность по отношению к базовой конфигурации `1 × 1`, а не как абсолютную загрузку аппаратных ресурсов.
5. **Профилирование MPE/Jumpshot дополняет измерения времени.** Временная диаграмма позволяет исследовать порядок выполнения фаз обмена и вычислений. Утверждать, что коммуникации полностью скрыты вычислениями, можно только при наличии достаточных измерительных данных, подтверждающих такое перекрытие.

Результаты относятся к конкретной конфигурации вычислительной среды и размеру сетки. Для других размеров задачи, оборудования и версий MPI/OpenMP оптимальное соотношение процессов и потоков может отличаться.

### Профилирование MPE / Jumpshot

Для анализа временной организации алгоритма предусмотрена версия программы с инструментированием MPE. В трассировке выделяются четыре фазы:

- `1_Halo_Exchange` — упаковка данных и запуск неблокирующих MPI-обменов;
- `2_Compute_Internal` — вычисление внутренних точек локальной подобласти;
- `3_Waitall` — ожидание завершения обменов;
- `4_Compute_Boundary` — обновление ghost-слоёв и вычисление граничных точек.

Для просмотра трассировки используется Jumpshot-4 из комплекта SLOG2SDK. Подробная инструкция по установке, запуску и анализу временной диаграммы приведена в отчёте по лабораторной работе.

> **Важно:** наличие небольшого времени `MPI_Waitall` само по себе не доказывает полного перекрытия коммуникаций и вычислений. Выводы следует делать на основании временной диаграммы и измерений отдельных этапов.
