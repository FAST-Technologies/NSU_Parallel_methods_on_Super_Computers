202/*
203 The following documentation has little resemblance to current CLOG-2
204 format. They are kept here for historical reference purpose.
205 2/17/2005 Anthony Chan
206*/
207/*
208The format:
209
210Each line:
211 type process task data cycle timestamp [comment]
212
213 type - nonnegative integer representing a user-defined event type
214 process - an integer representing the process in which the event occurred
215 task - an integer representing a different notion of task. Usually
216 ignored.
217 data - an integer representing user data for the event
218 cycle - an integer representing a time cycle, used to distinguish
219 between time returned by a timer that "rolls over" during
220 the run
221 timestamp - an integer representing (when considered in conjuction
222 with the cycle number) a time for the event. Upshot treats
223 the units as microseconds
224 comment - an optional character string representing user data. Currently
225 12 character maximum, will soon hopefully be any length (really!)
226
227All events from -100 to -1 are reserved header information events. When
228a log is produced, all [-100,-1] events will be moved to the top of the
229logfile and have their timestamps set to 0.
230
231All event from -101 and below are reserved system events. This is to
232provide some standardization for the logfiles, so various interpreting
233programs can glean similar data from the same logfile. All [-101,...)
234events will have valid timestamps and will be left in time-sorted
235order in the logfile.
236
237Formats for reserved types:
238
239 -1 Creation data *not used*
240 Comment: Creator and date
241
242 -2 Number of events in the logfile *not used*
243 Data: number of events
244
245 -3 Number of processors in the run
246 Data: number of processes
247
248 -4 Number of tasks used in the run *not used*
249 Task: number of tasks
250
251 -5 Number of event types used *not used*
252 Data: number event types
253
254 -6 Start time of the run
255 Timestamp: start time
256
257 -7 End time of the run
258 Timestamp: end time
259
260 -8 Number of times the timer cycled
261 For example, if the timer's units are in microseconds, and it has a
262 range of 0 - 2^32, and a run lasts 3 hours (range=4294 seconds, 3 hours=
263 10800 seconds), the timer would have cycled at least twice.
264 Data: number of timer cycles
265
266 -9 Decription of event types *not used*
267 Data: event type
268 Comment: Description
269
270 -10 printf string for event types *not used*
271 Data: event type
272 Comment: printf string
273
274 -11 Rollover point
275 The point at which the timer values 'rollover'
276 Timestamp: rollover point
277
278 -13 State definition
279 Define a state based on the events that signal the beginning and end
280 of the state. Also, define what to call the state and what color/
281 stipple pattern to give it in a graphical visualization tool.
282 Task: start event
283 Data: end event
284 Comment: color:bitmap state name
285
286 example: -13 0 3 4 0 0 Green:boxes Rhode Island
287 An event with type 3 will signify the entrance into a 'Rhode Island'
288 state. An event wil type 4 will signify the exit of the 'Rhode Island'
289 state.
290
291 States may be overlapped (enter a 'Rhode Island' state while in a
292 'Wisconsin' state while in a 'Nevada' state), and the state name may
293 have whitspace in it.
294
295 -100 Synchronization event
296 Sync events are used internally to sychronize timers on the various
297 processes. They do not appear in the logfiles.
298
299 -101 Send message
300 Represents the sending of a message
301 Data: process ID of the receiving process
302 Comment: <message-type tag of message> <size of the message, in bytes>
303
304 -102 Receive message
305 Represents the receiving of a message
306 Data: process ID of the sending process
307 Comment: <message-type tag of message> <size of the message, in bytes>
308
309*/
