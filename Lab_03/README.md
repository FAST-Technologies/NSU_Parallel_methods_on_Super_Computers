# Лабораторная работа №3: Параллельное умножение матриц на GPU с использованием CUDA

## Сравнение алгоритмов Naive, Tiled и библиотеки cuBLAS

Данный репозиторий содержит реализацию и исследование производительности параллельного умножения квадратных матриц $C = A \times B$ на графическом процессоре с использованием технологии NVIDIA CUDA.

В проекте реализованы три собственных CUDA-алгоритма и библиотечный вариант на основе cuBLAS. Дополнительно исследуется влияние типа памяти, использования CUDA Streams, размера матриц и точности вычислений на производительность.

---

## 📋 Описание проекта

**Цель работы** — изучить способы параллельного умножения матриц на GPU, реализовать CUDA-ядра с использованием глобальной и разделяемой памяти, сравнить их производительность с библиотекой cuBLAS и исследовать влияние различных стратегий работы с памятью.

### Реализованные алгоритмы

1. **Naive (Global Memory)**
   Наивный алгоритм, в котором один CUDA-поток вычисляет один элемент результирующей матрицы $C_{ij}$, считывая всю $i$-ю строку матрицы $A$ и весь $j$-й столбец матрицы $B$ напрямую из глобальной памяти GPU.

2. **Static Tiled (Shared Memory)**
   Блочный алгоритм с использованием статически выделяемой разделяемой памяти. Матрицы разбиваются на тайлы. Потоки блока кооперативно загружают фрагменты исходных матриц в Shared Memory, синхронизируются и повторно используют загруженные данные при вычислении элементов результирующей матрицы.

3. **Dynamic Tiled (Shared Memory)**
   Вариант блочного алгоритма, использующий динамически выделяемую разделяемую память. Размер используемой памяти определяется при запуске CUDA-ядра.

4. **cuBLAS**
   Высокооптимизированной аппаратной реализации от NVIDIA, библиотечная реализация матричного умножения с использованием функций `cublasSgemm` для `float` и `cublasDgemm` для `double`, с методом «прогрева» (warm-up) для исключения накладных расходов на инициализацию.

### Дополнительные возможности

- **Несколько стратегий работы с памятью:** Pageable, Pinned, Pageable Streams, Pinned Streams, а также Unified Memory — в зависимости от платформы и поддержки CUDA.
- **Потоковое выполнение:** обработка матриц частями с использованием нескольких CUDA Streams.
- **Два типа вычислений:** `float` и `double`, выбираемые при конфигурации проекта.
- **Автоматическая верификация:** сравнение вычислений GPU с CPU-эталоном для матриц размером до $1024\times1024$.
- **Проверка крупных матриц:** при $N>1024$ результат Naive CUDA используется как эталон для сравнения остальных GPU-алгоритмов.
- **Измерение производительности:** использование CUDA Events (`cudaEvent_t`) с микросекундной точностью и повторных запусков с предварительным прогревом.
- **Сохранение результатов:** экспорт измерений в CSV для последующего анализа.
- **Кроссплатформенная сборка:** поддержка Windows (MSVC) и Linux (GCC/Clang) с использованием CMake.
- **Документирование кода:** возможность автоматической генерации документации Doxygen.
- **Визуализация**: два Python-скрипта строят графики времени, ускорения и эффективности.
- **Автоматизация:** Скрипт `benchmark.ps1` и `benchmark.sh` тестирует различные комбинации размеров и блоков, выбирая минимальное время из 3 запусков.

## 🧠 Стратегии работы с памятью

В проекте реализованы следующие стратегии.

| Стратегия | Описание |
|---|---|
| `Pageable` | Использование обычной pageable host memory |
| `Pinned` | Использование закреплённой host memory, выделяемой через `cudaMallocHost` |
| `Pageable Streams` | Потоковая обработка частей матриц с использованием pageable memory |
| `Pinned Streams` | Потоковая обработка с использованием pinned memory |
| `Unified Prefetch` | Использование Unified Memory с предварительным перемещением данных через `cudaMemPrefetchAsync` |
| `Unified Managed` | Использование управляемой памяти, выделяемой через `cudaMallocManaged` |

Набор доступных стратегий зависит от операционной системы и возможностей GPU.

В частности:

- В Windows программа использует `Unified Managed`.
- В Linux программа добавляет `Unified Prefetch`, если устройство поддерживает `concurrentManagedAccess`.
- Если необходимая возможность отсутствует, соответствующая стратегия пропускается.

Поэтому состав экспериментальных данных на разных платформах может отличаться.

### Потоковая обработка

Для стратегий с суффиксом `Streams` матрица $A$ и результирующая матрица $C$ обрабатываются частями по строкам. Матрица $B$ загружается на GPU отдельно и используется всеми потоками.

В текущей конфигурации используются четыре CUDA Streams.

Такой подход позволяет организовать передачу данных и вычисления в нескольких потоках исполнения. Однако эффективность потоковой обработки зависит от размера матрицы, объёма передаваемых данных и особенностей аппаратной платформы.

## ⏱️ Методика измерения производительности

Для каждой комбинации размера матрицы, стратегии памяти и алгоритма выполняются:

- один предварительный запуск (warm-up);
- пять измеряемых запусков.

Перед каждым измеряемым запуском результирующая матрица очищается. Для анализа производительности программа фиксирует время передачи данных, выполнения CUDA-ядра и обратной передачи результата.

Используются следующие метрики:

| Метрика | Описание |
|---|---|
| `H2D_ms` | Время передачи данных с CPU на GPU |
| `Kernel_ms` | Время выполнения вычислительного ядра |
| `D2H_ms` | Время передачи результата с GPU на CPU |
| `TotalMedian_ms` | Медианное полное время выполнения |
| `TotalMin_ms` | Минимальное полное время выполнения |
| `Verified` | Результат проверки корректности |

Для анализа алгоритмов умножения основной метрикой является `KernelMedian` — медианное время выполнения вычислительного ядра.

Для сравнения стратегий памяти используется `TotalMedian`, поскольку полное время учитывает не только вычисления, но и накладные расходы на передачу данных и организацию выполнения.

В потоковых режимах времена отдельных стадий рассчитываются с учётом обработки нескольких частей матрицы и работы нескольких потоков. Поэтому их не следует интерпретировать как простую сумму независимых последовательных операций.

### Проверка корректности

Для матриц размером $N\leq1024$ дополнительно вычисляется CPU-эталон с использованием последовательного алгоритма умножения матриц.

Для матриц большего размера CPU-вычисление пропускается. В качестве эталона используется результат алгоритма Naive CUDA для соответствующей стратегии памяти.

Проверка выполняется с использованием абсолютной и относительной погрешностей. Допуски зависят от выбранного типа данных:

- `float`: абсолютный допуск $10^{-3}$, относительный допуск $3\cdot10^{-5}$;
- `double`: абсолютный и относительный допуски $10^{-10}$.

**Важно:** для матриц $N>1024$ успешная проверка означает согласованность результата с GPU-эталоном Naive в пределах заданного допуска. Она не является независимой проверкой относительно CPU-эталона.

## 📊 Обработка и анализ результатов

Для сравнения вычислительных алгоритмов используется медианное время выполнения ядра.

Ускорение относительно наивного алгоритма вычисляется по формуле:

$
S_{\text{Static}}=
\frac{T_{\text{Naive}}}{T_{\text{Static}}}
$

$
S_{\text{Dynamic}}=
\frac{T_{\text{Naive}}}{T_{\text{Dynamic}}}
$

где $T$ — медианное время выполнения CUDA-ядра для соответствующего алгоритма.

Интерпретация результатов:

- $S>1$ — блочный алгоритм быстрее Naive;
- $S=1$ — производительность алгоритмов одинакова;
- $S<1$ — блочный алгоритм медленнее Naive.

При сравнении стратегий памяти следует использовать полное медианное время `TotalMedian_ms`, а не только время выполнения ядра.

Для корректного анализа необходимо учитывать статус `Verified`. Результаты, не прошедшие проверку, не следует включать в итоговые сравнения производительности как корректные вычисления.

При сравнении `float` и `double` необходимо учитывать различия в объёме занимаемой памяти, точности вычислений и аппаратной производительности GPU.

## ⚠️ Ограничения и особенности текущей реализации

1. Размер блока потоков задаётся на этапе компиляции через `TILE_SIZE` в `config.hpp`.
2. Передача размера блока через командную строку не позволяет динамически изменить конфигурацию CUDA-ядра.
3. Одиночный режим ограничен размером матрицы 8192, тогда как полный бенчмаркинг включает размер 16384.
4. CPU-эталон используется только для матриц размером не более 1024.
5. Доступность Unified Memory и Unified Prefetch зависит от возможностей GPU и платформы.
6. Время полного выполнения может существенно отличаться от времени CUDA-ядра из-за передачи данных и дополнительных накладных расходов.
7. Для корректного сравнения результатов необходимо учитывать тип данных, размер блока, стратегию памяти, размер матрицы и аппаратную платформу.
