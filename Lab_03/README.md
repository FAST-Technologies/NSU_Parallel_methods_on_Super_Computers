# Лабораторная работа №3: Параллельное умножение матриц на GPU (CUDA)
## Сравнение методов Naive, Tiled (Shared Memory) и cuBLAS

Данный репозиторий содержит реализацию и исследование производительности трёх различных методов умножения квадратных матриц $C = A \times B$ на графическом процессоре (GPU) с использованием технологии NVIDIA CUDA. Проект разработан в рамках учебного курса по параллельным методам вычислений..

---

## 📋 Описание и ключевые особенности

**Цель работы** — реализовать и сравнить производительность различных подходов к умножению матриц $C = A \times B$ на GPU, исследовать влияние размера блока потоков и решётки блоков на производительность, а также сравнить ручную оптимизацию с использованием разделяемой памяти против высокооптимизированной библиотеки cuBLAS.

**Реализованные методы:**

1. **Наивный алгоритм (Naive / Global Memory).**
   Каждый поток вычисляет один элемент результирующей матрицы $C_{ij}$, считывая всю $i$-ю строку матрицы $A$ и весь $j$-й столбец матрицы $B$ напрямую из глобальной памяти видеокарты.

2. **Блочный алгоритм (Tiled / Shared Memory).** Матрицы разбиваются на тайлы. Потоки кооперативно загружают фрагменты в быструю разделяемую память (Shared Memory), синхронизируются через `__syncthreads()` и выполняют вычисления, многократно используя загруженные данные. Реализованы два варианта: со *статическим* и *динамическим* выделением памяти.

3. **Библиотека cuBLAS.** Использование высокооптимизированной аппаратной реализации от NVIDIA с методом «прогрева» (warm-up) для исключения накладных расходов на инициализацию.

**Особенности реализации:**
* **Кроссплатформенность:** Код корректно компилируется как в Windows (MSVC), так и в Linux (GCC/Clang).
* **Чистая архитектура:** CUDA-ядра вынесены в отдельный заголовочный файл (`matrix_kernels.hpp`) с полной документацией Doxygen.
* **Гибкий запуск:** Размер матрицы и блока передаются через аргументы командной строки.
* **Автоматическая верификация:** Результаты GPU сравниваются с эталонным CPU-умножением (для $N \le 1024$).
* **Автоматизация:** Скрипт `benchmark.ps1` и `benchmark.sh` тестирует различные комбинации размеров и блоков, выбирая минимальное время из 3 запусков.
* **Три независимых ядра** в одном исполняемом файле для прямого сравнения на одних и тех же данных.
* **Точные замеры времени**: используется механизм CUDA Events (`cudaEvent_t`) с микросекундной точностью.
* **Визуализация**: два Python-скрипта строят графики времени, ускорения и эффективности.
* **Генерация документации**: автоматическая сборка HTML-документации через Doxygen.

## 🚀 Запуск и бенчмаркинг
### **Ручной запуск**
Программа принимает до двух аргументов:
1. **N** — размер квадратной матрицы (по умолчанию 1024).
2. **BLOCK_SIZE** — размер блока потоков (по умолчанию 16).
   ```bash
     # Запуск с матрицей 1024×1024 и блоком 32×32
     ./build/Lab_03 1024
        
     # Запуск с матрицей 2048×2048 и блоком 16×16
     ./build/Lab_03 2048 16
   ```

   ```cmd
   .\Release\Lab_03.exe 1024 16
   .\Release\Lab_03.exe 2048 32
   ```

Программа выведет время выполнения каждого из трёх методов и (для **N ≤ 512**) результат верификации.

### **Автоматический бенчмаркинг**

**Для Linux**

В корне проекта находится скрипт `benchmark.sh`, который автоматически тестирует различные комбинации размеров матриц (256, 512, 1024, 2048) и размеров блоков (16, 32). Для каждой конфигурации выполняется 3 запуска, берётся минимальное время.

   ```bash
   # Сделать скрипт исполняемым (один раз)
   chmod +x benchmark.sh
   
   # Запустить бенчмарк
   ./benchmark.sh
   ```

Скрипт выведет таблицу в терминал, которую можно напрямую скопировать в отчёт.

** Для Windows**

В корне проекта находится скрипт `benchmark.ps1`, который автоматически тестирует комбинации размеров матриц и блоков (по 3 запуска на конфигурацию).
1. Разрешите выполнение скриптов (требуется один раз, от имени администратора или с флагом Scope CurrentUser):
   ```powershell
   Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
   ```
2. Запустите бенчмарк из корня проекта:
   ```powershell
   .\benchmark.ps1
   ```

**(Для сохранения в файл используйте: .\benchmark.ps1 > output.txt)**

## 📊 Результаты исследования производительности

В ходе лабораторной работы проведены эксперименты по сравнению четырёх вариантов умножения квадратных матриц:

- **Naive (Global Memory)** — наивный алгоритм, использующий глобальную память видеокарты.
- **Tiled Static** — блочный алгоритм с использованием статической разделяемой памяти.
- **Tiled Dynamic** — блочный алгоритм с использованием динамической разделяемой памяти.
- **cuBLAS** — библиотечная реализация умножения матриц с использованием функции `cublasSgemm`.

Исследование проводилось на двух аппаратных платформах: серверном вычислительном узле с архитектурой Ada Generation и домашнем компьютере с видеокартой архитектуры Blackwell.

Для сравнения использовались квадратные матрицы размером от 256×256 до 8192×8192. В качестве размеров блока потоков исследовались конфигурации 2×2, 4×4, 8×8, 16×16 и 32×32. Ниже приведены результаты для блоков 16×16 и 32×32.

Время выполнения измерялось с помощью CUDA Events. Все значения приведены в миллисекундах.

Ускорение вычислялось относительно наивного алгоритма:

\[
S_{\text{Static}}=\frac{T_{\text{Naive}}}{T_{\text{Static}}}
\]

\[
S_{\text{Dynamic}}=\frac{T_{\text{Naive}}}{T_{\text{Dynamic}}}
\]

Значение ускорения больше единицы означает преимущество соответствующего блочного алгоритма перед наивной реализацией.

### 3. Анализ полученных результатов

По результатам проведённых экспериментов можно выделить следующие закономерности.

**1. Влияние размера блока потоков.**

Размер блока существенно влияет на производительность блочных алгоритмов. При использовании небольших блоков (2×2 и 4×4) наблюдается значительное увеличение времени выполнения. Это связано с ростом количества блоков, накладными расходами на их планирование и недостаточно эффективным использованием ресурсов GPU.

Блоки размером 16×16 и 32×32 в большинстве исследованных конфигураций обеспечивают более высокую производительность.

**2. Преимущества статической разделяемой памяти.**

На серверной видеокарте RTX 4000 SFF Ada Generation статический вариант Tiled демонстрирует преимущество перед динамическим вариантом практически на всех исследованных размерах.

На RTX 5060 Ti динамический вариант оказывается быстрее статического на небольших матрицах, однако при увеличении размера задачи преимущество чаще переходит к статическому варианту.

Таким образом, выбор способа выделения разделяемой памяти зависит от архитектуры GPU и параметров вычислительной задачи.

**3. Влияние размера матриц.**

При увеличении размера матриц возрастает объём вычислений, пропорциональный \(O(N^3)\). При этом блочный алгоритм позволяет повторно использовать загруженные в разделяемую память элементы исходных матриц.

Для небольших матриц накладные расходы на синхронизацию потоков могут снижать эффективность Tiled-алгоритма. Для крупных матриц повторное использование данных становится более значимым.

**4. Преимущества cuBLAS.**

Библиотека cuBLAS показывает наименьшее время выполнения среди исследованных реализаций.

Это объясняется использованием специализированных оптимизированных алгоритмов, учитывающих особенности архитектуры видеокарты, и аппаратных возможностей NVIDIA GPU.

При этом cuBLAS позволяет получить высокую производительность без необходимости самостоятельно реализовывать сложные алгоритмы оптимизации матричного умножения.

**5. Сравнение аппаратных платформ.**

Результаты экспериментов на серверном кластере и домашнем компьютере различаются. Это обусловлено различиями архитектур GPU, пропускной способности памяти, вычислительных ресурсов, версий CUDA Toolkit и программных сред.

Поэтому корректно сравнивать алгоритмы внутри каждой платформы, а не делать вывод о превосходстве одной видеокарты только на основании отдельных значений времени.

- Использование разделяемой памяти позволяет существенно ускорить умножение матриц по сравнению с наивной реализацией.
- Оптимальный размер блока зависит от размерности матриц и архитектуры GPU.
- Статическое и динамическое выделение разделяемой памяти демонстрируют различную эффективность на разных вычислительных платформах.
- Для небольших матриц накладные расходы на синхронизацию могут снижать эффективность блочного алгоритма.
- cuBLAS обеспечивает наилучшую производительность среди рассмотренных реализаций.

Таким образом, цель лабораторной работы достигнута: изучены способы параллельного умножения матриц на GPU, реализованы CUDA-ядра, проведены эксперименты с различными размерами матриц и блоков, а также выполнено сравнение собственных реализаций с библиотекой cuBLAS.

Результаты экспериментов подтверждают важность выбора оптимальной конфигурации запуска CUDA-ядер и применения специализированных библиотек для решения вычислительно сложных задач линейной алгебры.

Результаты относятся к конкретной конфигурации вычислительной среды и размеру матриц. Для другого оборудования и версий CUDA оптимальные параметры могут отличаться.

*Полные таблицы данных, графики ускорения и эффективности, а также подробный анализ представлены в [отчёте по лабораторной работе](./Report_on_Assignment_03_Yamshchikov.docx "Отчёт по проделанной работе").*
