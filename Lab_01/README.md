# Лабораторная работа №1: Параллельные циклы (OpenMP)
## Параллельная трассировка лучей (Ray Tracing)

Данный репозиторий содержит реализацию и исследование производительности параллельного алгоритма трассировки лучей с использованием спецификации OpenMP. Проект разработан в рамках учебного курса по параллельным методам вычислений.

За основу взята последовательная реализация мини-рейтрейсера: [georgy-schukin/mini-rt](https://github.com/georgy-schukin/mini-rt).

## 📋 Описание и внесенные изменения

**Основная цель работы** – распараллелить вычислительно сложный цикл рендеринга и исследовать влияние различных стратегий планирования (`schedule`) на производительность, учитывая высокий дисбаланс нагрузки (некоторые пиксели требуют множественных отражений/преломлений, а некоторые считаются мгновенно).

**Ключевые модификации исходного кода:**
1. Основной цикл в `main()` распараллелен директивой `#pragma omp parallel for collapse(N) schedule(runtime)`, где `N` – 1 или 2. Клауза `collapse` объединяет вложенные циклы, а `schedule(runtime)` позволяет выбирать стратегию планирования при запуске, через переменную окружения `OMP_SCHEDULE`, без перекомпиляции.
2. Внедрён высокоточный замер времени вычислений с использованием `std::chrono::high_resolution_clock` и `omp_get_wtime()` (операции ввода-вывода в замер не входят).
3. Создан автоматизированный Bash-скрипт (`benchmark.sh`) для проведения серии тестов с поиском минимального времени выполнения.

### Как переключаются `collapse` и `schedule`

| Параметр | Где задаётся | Как менять |
|:---------|:-------------|:-----------|
| `collapse(1)` / `collapse(2)` | В исходном коде, в директиве `#pragma omp parallel for` | Вручную поменять цифру в директиве и пересобрать проект (`make -j`). Это константа времени компиляции, через переменную окружения её задать нельзя |
| Стратегия планирования (`dynamic,16`, `static`, `static,1`, `guided,16`) | Переменная окружения `OMP_SCHEDULE` | При запуске, пересборка не нужна (работает благодаря `schedule(runtime)`) |
| Число потоков | Переменная окружения `OMP_NUM_THREADS` | При запуске, пересборка не нужна |

Директива в коде:

```cpp
#pragma omp parallel for collapse(2) schedule(runtime)   // collapse(1) или collapse(2) – меняется вручную
for (int x = 0; x < viewPlaneResolutionX; x++)
    for (int y = 0; y < viewPlaneResolutionY; y++) {
        const auto color = viewPlane.computePixel(scene, x, y, numOfSamples);
        image.set(x, y, color);
    }
```

Формат запуска:

```bash
OMP_NUM_THREADS=2 OMP_SCHEDULE="dynamic,16" ./test/minirt-test 1000 1000 10
```

> **Важно:** если в директиве указано `schedule(dynamic, 16)` (или любое другое явное значение), переменная `OMP_SCHEDULE` игнорируется. Она учитывается только при `schedule(runtime)`.

## 🛠️ Сборка проекта

1. Склонируйте репозиторий (если еще не сделали этого):
   ```bash
   git clone <URL этого репозитория>
   cd NSU_Parallel_methods_on_Super_Computers/Lab_01
   ```
2. Создайте директорию для сборки и перейдите в неё:
   ```bash
   mkdir mini-rt-build && cd mini-rt-build
   ```
3. Сконфигурируйте проект в режиме Release (с оптимизацией `-O3`):
   ```bash
   cmake ../mini-rt/src -DCMAKE_BUILD_TYPE=Release
   ```
4. Скомпилируйте проект, используя все доступные ядра:
   ```bash
   make -j
   ```

## 🚀 Запуск и бенчмаркинг
### **Ручной запуск**
Вы можете запустить рендеринг вручную, указав разрешение и количество сэмплов на пиксель (SPP). Параметры OpenMP задаются через переменные окружения:
   ```bash
   cd mini-rt-build
   OMP_NUM_THREADS=8 OMP_SCHEDULE="dynamic,16" ./minirt-test 1000 1000 10
   ```
*Результат будет сохранен в файл `raytracing.jpg`.*

### **Автоматическое тестирование**

В папке `Lab_01` доступен скрипт `benchmark.sh`, который автоматически прогоняет тесты для стратегий `dynamic,16`, `static`, `static,1` и `guided,16` при количестве потоков от 1 до 20. Для каждой комбинации выполняется несколько запусков, и выбирается минимальное время (согласно методике измерений). Значение `collapse` скрипт не меняет: для сравнения `collapse(1)` и `collapse(2)` измените директиву в коде, пересоберите проект и запустите скрипт ещё раз.

   ```bash
   chmod +x benchmark.sh
   ./benchmark.sh
   ```

### **Построение графиков**

   ```bash
   pip install -r requirements.txt   # matplotlib, numpy, seaborn
   python plot_benchmarks.py
   ```
При необходимости построить сразу три графика на одной картинке используйте `plot_results.py`.

## 📊 Краткие результаты исследования
Эксперименты проводились на сцене разрешением **1000x1000** с **10 сэмплами** на пиксель. Таблица показывает ускорение $S_P$ и эффективность $E_P$ на 20 потоках (это максимум для всех стратегий).

| **Стратегия** | **$S_{20}$, `collapse(1)`** | **$E_{20}$, `collapse(1)`** | **$S_{20}$, `collapse(2)`** | **$E_{20}$, `collapse(2)`** |
|:--------------|:------:|:------:|:------:|:------:|
| **Dynamic, 16** | 7.18x | 35.9% | **8.61x** | **43.0%** |
| **Static, 1**   | 8.10x | 40.5% | 8.18x | 40.9% |
| **Guided, 16**  | 6.12x | 30.6% | 6.26x | 31.3% |
| **Static**      | 3.87x | 19.4% | 4.11x | 20.5% |

Ускорение рассчитано относительно $T_1$ – времени той же программы (с OpenMP) на одном потоке для соответствующей стратегии и значения `collapse`. Время последовательной версии, собранной без OpenMP, – около 7.25 с.

### **Ключевые выводы:**
1. Наивное использование `schedule(static)` приводит к критическому падению эффективности из-за дисбаланса нагрузки (простои потоков).
2. Стратегии `dynamic, 16` и `static, 1` обеспечивают наилучшую масштабируемость, эффективно перераспределяя «тяжёлые» задачи между ядрами. При `collapse(2)` лучшей оказывается `dynamic, 16`: чанк в 16 итераций – это 16 пикселей. При `collapse(1)` тот же чанк – это 16 значений `x`, то есть 16 000 пикселей, и планировщику не хватает гранулярности, и вперёд выходит `static, 1`.
3. Падение эффективности ($E_P$) на 16–20 потоках обусловлено архитектурой процессора (Intel Core i7-12700H): при превышении количества физических P-ядер начинают использоваться логические потоки (Hyper-Threading) и энергоэффективные E-ядра, которые делят физические вычислительные ресурсы (ALU/FPU).
